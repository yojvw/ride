# 成员 B：共享单车骑行数据分析与需求预测

本目录保存成员 B 的完整分析 Notebook：[DAZUOYE.ipynb](DAZUOYE.ipynb)。项目使用 2024 年 1 月共享单车骑行记录，依次完成数据体检、时间规律分析、站点借还分析、潮汐站点识别和小时需求预测，最后导出结果表与站点检查建议。

阅读顺序为：

**读取数据 → 检查质量 → 处理时间与时长 → 分析需求规律 → 识别站点潮汐 → 建立预测模型 → 检查误差 → 导出结果。**

本文按照 Notebook 实际执行的代码和已保存的运行输出编写。它解释的是本目录的 Notebook；仓库总流程、正式脚本及小组约定请参阅[项目根目录 README](../../README.md)。

## 1. 数据与分析口径

原始文件为 `题5_共享单车骑行_202401.csv`，来自课程学习平台，包含 **238,834 条记录、13 个字段**。原始 CSV 约 46 MB，按仓库约定只在本地保存，不上传 GitHub。

| 字段 | 用途 |
| --- | --- |
| `ride_id` | 骑行订单编号，用于识别订单和检查重复 |
| `rideable_type` | 车辆类型：普通自行车或电助力车 |
| `started_at`、`ended_at` | 出发、到达时间，用于计算时长和归属时段 |
| `start_station_name`、`start_station_id` | 起点站名与站点编号 |
| `end_station_name`、`end_station_id` | 终点站名与站点编号 |
| `start_lat`、`start_lng` | 起点纬度与经度 |
| `end_lat`、`end_lng` | 终点纬度与经度 |
| `member_casual` | 用户类型：会员 `member` 或非会员 `casual` |

本 Notebook 的主要分析表为 `df_valid`：只排除时间无效、负时长和零时长记录，保留 **238,699 条正时长订单**。站点信息缺失的订单仍参与总体时间分析；站点级统计则只统计相应一端站点编号可识别的借出或归还事件。

这里的 `Mon-Fri`、`Sat-Sun` 分别表示周一至周五、周六至周日，仅按星期分类，没有额外识别法定节假日。

## 3. 每一步做了什么

下面按 Notebook 中非空代码单元的顺序说明。

### 第 1 步：读取原始数据

用 `pd.read_csv()` 读取 CSV，并输出行列数及前 3 行，确认文件和字段正确。订单编号、起终点站点编号按字符串读取，因为这些字段是标识符，不需要参加数值运算。

**输出：**原始表 `df_raw`，规模为 **238,834 × 13**。

### 第 2 步：做数据质量体检

为每列统计数据类型、缺失数量和缺失比例，同时检查整行重复及订单编号重复。

结果显示，缺失主要集中在站点信息：起点站名与编号各缺失 **37,220 条（15.58%）**，终点站名与编号各缺失 **39,741 条（16.64%）**；终点经纬度各缺失 **203 条**。整行重复和订单编号重复均为 **0**，因此没有实际执行删除重复订单。

起点、终点的缺失可能出现在同一条订单中，不能将这些缺失数量直接相加当作缺失订单数。

### 第 3 步：转换时间并计算骑行时长

将 `started_at`、`ended_at` 从文本转换为时间类型，用两者之差计算 `duration_min`，单位为分钟。无法转换的时间会标记为缺失，便于后续识别。

时间转换失败数为 **0**。原始时长中位数为 **8.75 分钟**，均值约 **14.77 分钟**，最长接近 25 小时；另有 **44 条负时长、91 条零时长**。这一步先展示问题，不把负时长取绝对值，以免掩盖错误。

### 第 4 步：建立正时长分析表，保留异常记录供追溯

将时间无效或时长不大于 0 的记录保存在 `df_bad_time`，其余记录形成 `df_valid`。

**输出：**排除 **135 条**，保留 **238,699 条**。再将正时长订单分为三组：

| 时长组 | 订单数 |
| --- | ---: |
| 不足 1 分钟 | 4,722 |
| 1—180 分钟（含两端） | 233,180 |
| 超过 180 分钟 | 797 |

这里的分组用于观察分布。Notebook 没有直接删除所有过短或过长的正时长订单。

### 第 5 步：检验时长筛选是否改变每日需求走势

另外建立 `df_1_180` 子集，将“全部正时长订单”和“1—180 分钟订单”的每日出发量放在一起比较，并计算每天被筛掉的比例。

筛选后总量约减少 **2.31%**，单日减少比例最高为 **3.94%**，两条每日需求曲线的整体走势接近。这一步用于检查结论对筛选规则是否敏感；后续主要分析仍使用 `df_valid`。

### 第 6 步：比较周一至周五与周末的小时需求

先按实际日期与小时汇总订单数，再分别计算两类日期在每个小时的平均订单量。采用“每小时、每天的平均值”，避免两类日期天数不同造成总量不可比。

周一至周五呈现早晚双峰，**08:00—09:00**和 **17:00—18:00**较突出，晚高峰高于早高峰；周末高需求时段主要在中午至下午。

### 第 7 步：用“星期 × 小时”热力图细看时间规律

将小时需求透视为 7 行 × 24 列的表，再绘制热力图，并列出每个星期的峰值小时。

本月周一至周五的平均需求峰值都出现在 **17:00—18:00**；周六、周日的峰值分别为 **12:00—13:00**和 **14:00—15:00**。热力图让高需求集中在哪些日期、哪些小时更直观。

### 第 8 步：比较会员类型与车型

按“会员类型 × 车辆类型”分组，计算订单数、时长中位数和占全部正时长订单的比例，再画各会员类型内部的车型占比图。

| 用户类型 | 车型 | 订单数 | 时长中位数（分钟） |
| --- | --- | ---: | ---: |
| 非会员 | 普通自行车 | 27,126 | 12.63 |
| 非会员 | 电助力车 | 34,612 | 9.30 |
| 会员 | 普通自行车 | 89,537 | 8.28 |
| 会员 | 电助力车 | 87,424 | 8.13 |

非会员订单中电助力车占 **56.06%**，会员订单中占 **49.40%**。这些是订单构成和时长差异，不能仅凭此判断出行目的或差异的原因。

### 第 9 步：重新读取数据，恢复分析起点

Notebook 中间再次读取同一个 CSV，重新执行时间转换、时长计算和正时长筛选，恢复 `df_valid`。

这不是额外清洗规则，也不是把两份数据相加。恢复后的记录数仍为 **238,699 条**，后续站点和建模分析沿用这一口径。

### 第 10 步：比较会员与非会员的日内分布

按“日期类型 × 会员类型”分别计算 24 个小时的订单占比，每个群体内部的占比加总为 100%，再比较曲线。

使用占比是为了比较出行时间的分布形状，而不是被会员与非会员样本量差异主导。周一至周五两组的峰值均在 17 点，周末均在 14 点；会员的早间集中程度更突出。

### 第 11 步：建立站点借还流量表

出发事件按 `started_at` 统计，到达事件按 `ended_at` 统计，窗口均限定为 **2024-01-01 至 2024-02-01 之前**。分别按站点编号汇总借出和归还次数，再合并成 `station_flow`。

两个指标的含义为：

- `net_outflow = departures - arrivals`：正值表示净流出，负值表示净流入。
- `total_events = departures + arrivals`：表示借还总活跃度，不是独立订单数。

站点编号可识别比例分别约为起点 **84.45%**、终点 **83.40%**。缺失编号的一端不会进入该端站点统计，但订单不会因此从总体时间分析中删除。

### 第 12 步：识别早晚流向相反的潮汐候选站点

限定周一至周五，分别统计早高峰 **07:00—10:00**与晚高峰 **16:00—19:00**的借出、归还事件，计算日均净流出。分母为本月全部 **23 个周一至周五日期**。

筛选早晚日均净流量一正一负的站点，再按“早晚两侧净流量绝对值的较小值”排序，选出 8 个候选站点。这种排序方式优先关注早晚两侧都比较明显的流向变化。

例如：

| 站点编号 | 早高峰日均净流出 | 晚高峰日均净流出 | 观察到的模式 |
| --- | ---: | ---: | --- |
| 31277 | -16.22 | 7.83 | 早间净流入、晚间净流出 |
| 31101 | 11.91 | -9.35 | 早间净流出、晚间净流入 |

### 第 13 步：检查潮汐方向是否逐日重复

建立完整的“23 个日期 × 8 个候选站点”组合，没有事件的组合补为 0，逐日检查早、晚高峰净流量是否都与月平均方向一致。

31277 站点有 **21 天（91.30%）**早晚两个方向都符合，31101 有 **20 天（86.96%）**。这一步用于避免只看月均值而忽略每天的差异；净流量为 0 的时段不计为方向一致。

### 第 14 步：展示站点活动的空间分布

将起点、终点坐标整理为相同格式，排除缺失或超出经纬度基本范围的坐标记录。对同一站点的坐标取中位数作为展示位置，再连接站点流量表。

绘制经纬度散点图，用颜色表示借还总次数，并标出 31277、31101 两个重点案例。共有 **761 个站点**，汇总后都获得了可用展示坐标。

这一步过滤的是用于定位的坐标记录，不是把相关订单从 `df_valid` 中全部删除；图形是经纬度散点展示，没有使用道路地图或计算实际骑行路线。

### 第 15 步：构造小时需求预测数据

把整个 1 月补齐为 **744 个小时**，每小时出发订单数 `rides` 是预测目标。输入特征共 8 个：

| 特征 | 含义 |
| --- | --- |
| `hour` | 当前小时 |
| `weekday` | 星期，周一为 0 |
| `is_weekend` | 是否为周六或周日 |
| `lag_1` | 前 1 小时的实际需求 |
| `lag_24` | 前一天同小时的实际需求 |
| `lag_168` | 前一周同小时的实际需求 |
| `mean_3` | 过去 3 小时的平均需求 |
| `mean_24` | 过去 24 小时的平均需求 |

滚动平均先执行 `shift(1)`，排除当前要预测的小时，避免将目标值混入输入。由于需要一周历史，最前面的 168 个小时不进入建模，最终有 **576 个小时样本**。

数据按时间先后划分，不随机打乱：

| 数据集 | 实际日期范围 | 小时数 | 用途 |
| --- | --- | ---: | --- |
| 训练集 | 1 月 8—20 日 | 312 | 学习模型 |
| 验证集 | 1 月 21—25 日 | 120 | 比较方法 |
| 测试集 | 1 月 26—31 日 | 144 | 最终评估 |

### 第 16 步：建立三种简单基线

分别直接使用“前一小时”“前一天同小时”“前一周同小时”的实际需求作为当前小时预测值，先检验简单规则的效果。

评价指标为 **MAE** 和 **RMSE**，均以每小时订单数计，越小越好。MAE 表示平均绝对误差，RMSE 对大误差更敏感。

| 验证集基线 | MAE | RMSE |
| --- | ---: | ---: |
| 前一天同小时 | 74.46 | 121.90 |
| 前一小时 | 113.45 | 166.33 |
| 前一周同小时 | 173.70 | 246.73 |

按验证集 MAE 选出“前一天同小时”作为后续主要对照，确保复杂模型的效果有参照。

### 第 17 步：训练随机森林并在验证集比较

用上述 8 个特征训练随机森林回归模型。主要参数为 200 棵树、最大深度 6、叶节点最少 3 个样本、`random_state=42`。

模型只使用训练集学习，再在验证集预测。验证集随机森林的 **MAE 为 64.63，RMSE 为 101.18**，相对最佳基线的 MAE 降低 **13.20%**。

这里没有进行大规模参数搜索，验证结果只对应当前这一组模型参数。

### 第 18 步：合并训练与验证数据，做最终测试

固定模型参数，将训练集与验证集合并为 **432 个小时**，复制同样配置的模型重新训练，再对保留的 **144 个测试小时**评估。

| 测试集方法 | MAE | RMSE |
| --- | ---: | ---: |
| 前一天同小时 | 158.29 | 239.46 |
| 随机森林 | 94.88 | 147.72 |

随机森林测试 MAE 相对基线降低 **40.06%**。测试采用逐小时滚动的一步预测：预测某小时的时候，允许使用该小时之前已经观察到的实际需求。这些结果不表示模型能在完全不知道后续观测的情况下，一次性预测未来整周。

### 第 19 步：拆解预测误差

计算每个测试小时的有符号误差和绝对误差，再按日期类型、早高峰、晚高峰及其他时段分别汇总，并列出误差最大的 5 个小时。

误差定义为“预测值减实际值”：正值为高估，负值为低估。周一至周五晚高峰的平均偏差约为 **-218.29 单/小时**，显示这一测试期存在晚高峰低估。

例如 1 月 26 日 17 点实际为 **1,517 单**，随机森林预测约 **808.78 单**。这一步帮助发现总体指标中被掩盖的薄弱时段。

### 第 20 步：形成检查建议并导出结果

把候选站点的早晚净流量与逐日稳定性合并，生成检查重点：

- 净流出时段：检查可用车辆，结合库存判断是否需要补车。
- 净流入时段：检查停车容量，结合库存判断是否需要疏解。

这里给出的是有数据依据的检查建议。仅靠骑行日志和净流量，无法确定实际缺车量、空车位数或最优调度车辆数，还需要实时库存、站点容量和调度成本。

结果保存到 Python 当前工作目录下的 `project_results/`。按上面的运行设置，这个目录位于仓库根目录。

## 5. 与仓库总流程的版本差异

根目录 README 给出的公共约定与本 Notebook 的实际口径存在以下差异，交叉核对结果时需要保留这些说明：

| 项目 | 本 Notebook | 根目录 README 的公共约定 |
| --- | --- | --- |
| 时长筛选 | 主分析保留全部正时长订单；另做 1—180 分钟的敏感性比较 | 正式清洗保留 1—1440 分钟，并剔除终点经纬度缺失 |
| 分析行数 | 238,699 | 正式清洗校验基准为 233,749 |
| 站点缺失 | 保留订单，站点级统计忽略缺失编号的一端 | 统一填充为“站点外停车” |
| 训练与测试 | 1 月 8—20 日训练，21—25 日验证，26—31 日测试 | 1 月 1—24 日训练，25—31 日测试 |
| 评价指标 | MAE、RMSE | RMSE、MAE、R² |

因此，本 Notebook 的结果应按其自身口径解释，不能直接当作正式脚本清洗基准或指标的复现值。形成全组汇总稿时，需要先统一数据、时间窗口和评估方式，再比较成员结果。

## 6. 结论的适用范围

- 当前只分析一个月的数据，时间规律和模型效果尚未经过跨月、跨季节检验。
- 站点分析只覆盖可识别的站点事件；数据以本月出发订单为基础，跨月到达及样本范围外的出发事件也可能影响月度借还净值。
- 预测特征没有包含天气、节假日、活动、实时车辆供给等信息，突发高峰仍可能低估。
- 潮汐规律和净流量可以帮助确定检查时段与候选站点，实际调度决策还需结合库存与容量。
